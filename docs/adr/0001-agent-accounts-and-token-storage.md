# ADR-0001: Модель аккаунтов агентов и хранение per-agent токенов YouTrack

- Задача: #3243 (проект YTMCP, project_id=1910)
- Статус: Accepted
- Дата: 2026-07-29
- Автор: architect
- Опирается на: research_brief задачи #3242 (аудит YouTrack REST API, артефакт #124 / knowledge #91), интейк #3241 (system_analyst, project memory #89), код `admin.py`/`admin_cli.py` модуля admin-cli на момент написания (коммит `a4e89e3`, ветка `main`)

## 1. Контекст

Оркестратор должен уметь заводить агентам аккаунты в YouTrack и раздавать им персональные токены для работы через MCP-сервер (`youtrack_mcp/server.py`, идентичность агента задаётся переменной окружения `YOUTRACK_TOKEN` конкретного инстанса — сервер identity-less, см. project memory #89). Это затрагивает три архитектурных риска сразу:

1. **Auth/identity** — модель учётных записей (per-agent vs общий аккаунт).
2. **Billing** — YouTrack-лицензия ограничивает число активных пользователей (YT Cloud free = 10 + 3 helpdesk); создание сверх лимита не блокируется API, но новый пользователь создаётся сразу `banned=true` (не может логиниться/использовать токен).
3. **Приватные токены** — постоянные токены (`permanent token`, `Bearer perm-...`) не должны попадать в код, репозиторий, публичные логи или тело задачи/отчёта.

Бизнес-логика провижининга уже реализована и покрыта тестами в `admin-cli` (`AdminClient.provision_agent/list_users/ban_user/delete_user`, `youtrack-admin` CLI) — идемпотентна (create-or-reuse по `login`), выдаёт роль и permanent-токен со scope `YouTrack` + `YouTrack Administration`. Модуль `admin-cli` помечен `forbidden=true` (auth/identity-зона) — любой мерж в него требует отдельного Founder Approval независимо от обычной gate-цепочки.

Открытый вопрос, который не закрывает существующий код: **как оркестратор (Core, project_id=7) хранит и раздаёт выпущенные per-agent токены** конкретным агентским MCP-конфигам, и как Core однократно принимает `YOUTRACK_ADMIN_TOKEN` от Основателя. Это вне репозитория `youtrack-mcp-server`.

## 2. Решение 2.1 — модель аккаунтов: 1 YouTrack-аккаунт на агента

**Выбрано:** один YouTrack/Hub-пользователь на одного агента артели (login = slug агента, напр. `agent-alpha`), с ролью `contributor` по умолчанию (Read/Create Issue, Update Issue, Create Comment).

**Обоснование:**
- Уже так реализовано в `provision_agent` — нулевая стоимость миграции, изменений кода `admin.py` не требуется.
- Нативная атрибуция: issue/comment/history в YouTrack отображают, какой именно агент выполнил действие — важно для аудита и ревью работы агентов, для отладки инцидентов, и в целом соответствует принципу артели «нет артефакта без владельца».
- Стандартная YouTrack permission-модель применяется без модификаций (built-in роли, scope токена), не нужно городить кастомную проверку прав поверх общего аккаунта.
- Точечная ревокация: `ban_user`/`delete_user` отзывают доступ ровно одному агенту, не затрагивая остальных. При общем аккаунте компрометация или отзыв токена одного «источника» обрушивает доступ всем.

**Отклонённая альтернатива: общий service-account + разграничение через custom field**
- Экономит лицензионные seats (один пользователь вместо N), что снижает риск seat-exhaustion.
- Но: теряется нативная атрибуция (все issue/comment будут «от лица» одного технического пользователя, custom field — самодельная, не проверяется YouTrack permission-моделью, легко забыть проставить); один общий permanent-токен = одна точка отказа при компрометации/ревокации (нельзя отозвать доступ одному агенту, не оборвав всех); YouTrack `run_command` (смена статуса) и permission-система в принципе спроектированы вокруг per-user identity, борьба с этим — архитектурный долг без реальной экономии инженерных усилий.
- Отклонено: экономия seats не перевешивает потерю атрибуции/аудита и рост сложности. Риск seat-exhaustion закрывается решением 2.3 (machine-readable сигнал), а не сменой модели аккаунтов.

**Дальнейшая цена решения:** расход лицензионных seats линеен числу агентов — управляется решением 2.3.

## 3. Решение 2.2 — хранение per-agent токенов

**Выбрано:** переиспользовать существующую конвенцию артели для приватных per-agent значений, без создания нового отдельного хранилища.

В артели уже есть ровно такой паттерн для другого типа приватного per-agent значения — `TelegramBinding.bot_token` (`core/artel_core/models.py:78-91`, таблица `telegram_bindings`, поле `bot_token: String(128)` в БД Core, наружу отдаётся только маскированный хвост `bot_token_tail` через API — `core/artel_core/api/agents.py:69`, значение обязательно только при первичной привязке — `agents.py:144-148`). Токен передаётся в процесс агента через env-инъекцию раннера, никогда не пишется в файл репозитория, публичный лог или тело задачи/отчёта.

**Решение по YouTrack-токену — зеркалим этот же паттерн:**
1. В Core (project_id=7, модуль `core`) добавляется аналогичная сущность (условно `YoutrackBinding`: `agent_id` FK, `login`, `token` (полный permanent-токен, хранится в БД Core как есть — тот же уровень защиты, что у `bot_token`, отдельного шифрования на уровне приложения в текущей архитектуре Core нет ни для одного приватного значения), опционально `license_status`, см. 2.3).
2. `YOUTRACK_TOKEN` инжектируется per-agent раннером в окружение процесса MCP-сервера этого агента — тем же механизмом, каким сейчас инжектируется `GITHUB_TOKEN`/`BOT_TOKEN` (`runner/artel_runner/workspace.py`).
3. Токен агента никогда не появляется в теле задачи, отчёте, публичном логе; наружу (API/UI) отдаётся только маска (по аналогии с `bot_token_tail`).
4. `YOUTRACK_ADMIN_TOKEN` (Hub admin-scope, право создавать/банить пользователей) — принимается от Основателя **один раз** как приватное значение исключительно на уровне процесса провижининга (окружение вызова `youtrack-admin`/`AdminClient`), никогда не раздаётся per-agent раннерам и не хранится в общей таблице агентских токенов — это отдельное, более привилегированное значение.

**Отклонённая альтернатива: новое отдельное централизованное хранилище приватных значений (класс Vault/AWS-менеджер-конфиденциальных-значений)**
- Более «правильно» в вакууме (ротация, аудит доступа, шифрование at rest из коробки), но в артели такого сервиса сейчас нет **ни для одного модуля** — вводить его ради одного YouTrack-токена создаёт новую инфраструктурную зависимость, новый forbidden-периметр, новый порог входа для всех агентов, без соразмерной выгоды на этом масштабе (артель — не мультитенантная SaaS, число агентов небольшое).
- Отклонено сейчас; зафиксировать как технический долг — если число типов приватных значений на агента вырастет (не только Telegram и YouTrack), пересмотреть и завести отдельный ADR на общий механизм хранения приватных значений для всех модулей разом, а не точечно под YouTrack.

**Явный гэп на момент ADR:** `youtrack-admin` CLI сейчас только human-readable (`print`), интерфейс для оркестратора уже закрыт по AC задачи #3241 как MCP-инструменты (`provision_agent`/`list_agents`/`revoke_agent`), а не CLI `--json` — эта развилка была решена PM/Founder раньше (decision #90/#93) и ADR её не переоткрывает.

## 4. Решение 2.3 — лицензионные seats

**Выбрано:** явный machine-readable сигнал по факту ответа Hub, а не pre-check квоты.

Текущий `provision_agent` (см. `admin.py:224-241`) не проверяет остаток лицензии и не сигнализирует, что новый пользователь создан `banned=true` из-за превышения лимита seats — это реальный гэп в уже написанном коде.

**Контракт для доработки (вне скоупа этого ADR как кода, но фиксируется здесь как требование к следующей задаче):**
- `Agent` dataclass дополняется полем `license_status: Literal["active", "seat_exhausted_banned"]`, вычисляемым по полю `banned` в ответе Hub сразу после `create_user`.
- При `seat_exhausted_banned` — `provision_agent` не должен молча отдавать «рабочий» токен: либо выбрасывает `LicenseLimitError`, либо возвращает `Agent` с этим статусом и ненулевым кодом возврата в CLI, чтобы вызывающий оркестратор не считал агента готовым к работе.

**Отклонённая альтернатива: pre-check квоты перед созданием пользователя**
- Нет подтверждённого кросс-edition (Cloud/Server/зависит от версии) публичного license-эндпоинта, на который можно надёжно опереться.
- TOCTOU-гонка при параллельном провижининге нескольких агентов делает pre-check ненадёжным в любом случае — между проверкой и созданием лимит может быть исчерпан другим параллельным вызовом.
- Отклонено: post-hoc сигнал по факту `banned` в ответе `create_user` — единственный источник истины, не подверженный гонке.

**Дополнительно:** ban_user (revoke-agent, уже реализован) освобождает seat без потери истории — это верная стратегия управления местами при масштабировании числа агентов, отдельного решения не требует.

## 5. Пункты, требующие отдельного Founder Approval до реализации

Независимо от того, что показывают структурные поля карточки Core (`risk`/`requires_founder_approval`/`forbidden` — известный гэп тулинга, см. knowledge #86, могут быть выставлены по умолчанию неверно для этой ветки задач):

1. **Реальный автоматический вызов `create_user`/`provision_agent`** из оркестратора/CI без участия человека — прямой billing-impact (расход лицензионных seats).
2. **Выдача и распространение `YOUTRACK_ADMIN_TOKEN`** (scope `YouTrack Administration`, право создавать/банить пользователей) в окружение любого процесса — самое привилегированное значение во всей схеме.
3. **Хранение per-agent `YOUTRACK_TOKEN` в БД Core** — новая таблица/колонка с приватным значением, требует того же уровня контроля, что и существующий `TelegramBinding.bot_token` (прецедент есть, но каждое новое место хранения такого значения — отдельное решение, не «по умолчанию ок»).
4. **Автоматическое массовое банение агентов** ради освобождения seats (если такая логика когда-либо будет автоматизирована, а не по явной команде) — необратимо влияет на доступ агентов, требует отдельного approve.
5. **Любой мерж в `admin.py`/`admin_cli.py`** (модуль `admin-cli`, `forbidden=true`) — только после отдельного Founder approve, независимо от обычной gate-цепочки qa→security→finops→team_lead.

## 6. Последствия

- Код `admin.py`/`admin_cli.py` в текущем виде **не меняется** этим ADR — модель аккаунтов подтверждена как уже реализованная.
- Открывается путь для двух отдельных задач вне скоупа этого ADR (запрошены как декомпозиция, не заведены архитектором самостоятельно):
  1. Доработка `provision_agent`/`Agent`/CLI под контракт `license_status` из раздела 4 (project_id=1910, компонент `admin-cli`, forbidden-зона, требует Founder Approval до мержа).
  2. Реализация в Core (project_id=7, компонент `core`) хранения/раздачи per-agent YouTrack-токенов по паттерну `TelegramBinding` из раздела 3 + приём `YOUTRACK_ADMIN_TOKEN` от Основателя (forbidden-зона: auth/приватные значения, требует Founder Approval до мержа).
- Технический долг зафиксирован: если появится третий тип приватного per-agent значения помимо Telegram/YouTrack — пересмотреть точечный паттерн `*Binding.token` в пользу общего механизма хранения приватных значений отдельным ADR.
